Conceptos de IA y LLM que usa la aplicación

La app es un sistema multiagente que analiza acciones, pero su valor real es didáctico: implementa —en un tamaño legible— casi todo el vocabulario moderno de ingeniería con LLMs. Esta guía nombra cada concepto, dice dónde vive en el código, responde las preguntas que surgen al leerlo y propone por dónde seguir.

01Conceptos de IA y LLM, y dónde viven

Cada tarjeta es un concepto que podrías encontrar en cualquier paper o entrevista, con su traducción exacta a este repositorio. Si podés señalar el archivo, entendiste el concepto.

Sistema multiagente

multi-agent system

Varios agentes especializados —datos, técnico, riesgo, escéptico, decisión— resuelven en conjunto una tarea que ninguno resuelve solo. La especialización reduce el contexto que cada uno necesita y hace auditable el razonamiento.

Dónde: agents/*.py, enum AgentName

Orquestación centralizada

orchestrator / hub-and-spoke

Un coordinador conoce el guion; los agentes no se conocen entre sí. Es lo contrario de una "swarm" totalmente descentralizada: menos emergencia, mucha más previsibilidad y depuración.

Dónde: Orchestrator.analyze_symbol()

Paso de mensajes tipado

typed message passing

Los agentes no comparten memoria: intercambian sobres inmutables (AgentMessage) con emisor, receptor, tipo y payload. in_reply_to encadena petición y respuesta en hilos.

Dónde: models.py, MessageType

Comunicación directa entre agentes

peer-to-peer agent messaging

El agente de riesgo le pide más histórico a market_data, y el escéptico reta al técnico, sin pasar por el coordinador como decisor —pero sí por el mismo canal, así nada queda invisible.

Dónde: info_request, challenge

Tool calling

function calling

El modelo no calcula: pide que se ejecute una función Python declarada con nombre, descripción y JSON Schema. Aquí algunas herramientas calculan (compute_risk_metrics) y otras envían mensajes reales a otros agentes (request_history).

Dónde: Tool = ToolSpec + handler

Bucle agéntico

agent loop / ReAct

Ciclo modelo → herramienta → resultado → modelo, hasta que el modelo devuelve el JSON final. El agente decide qué mirar y cuándo pedir más datos, con un tope de pasos.

Dónde: BaseAgent.run_agent_loop(), AGENT_MAX_STEPS

Salida estructurada

structured output / JSON mode

Cada agente exige un JSON conforme a un esquema (RISK_SCHEMA, TECH_SCHEMA…). Sin esto, un sistema multiagente no puede encadenar salidas de forma fiable.

Dónde: complete_json(), schema= en chat()

Prompt de sistema y roles

system prompt · role separation

El prompt fija el papel del modelo. En modo rules es explícito: "no cambies la postura; solo explícala". Separar quién decide de quién redacta es una decisión de arquitectura, no de estilo.

Dónde: SYSTEM_PROMPT, AGENT_SYSTEM_PROMPT

Prompting por capas

layered prompt composition

Ningún prompt está suelto ni en un fichero de texto: cada llamada se compone en código con tres capas —sistema, instrucciones de la tarea y mensaje de usuario generado por plantilla— más las herramientas y el esquema de salida.

Dónde: render_agent_prompt(), *_INSTRUCTIONS

La herramienta también es prompt

tool description as instruction

La descripción y el JSON Schema de cada ToolSpec son lo único que el modelo tiene para decidir cuándo usarla. Cambiar esa frase cambia el comportamiento tanto como editar el prompt.

Dónde: ToolSpec → tools / input_schema

Grounding / anclaje a hechos

grounding

Los números los produce código determinista (SMA, RSI, MACD, ATR, volatilidad, drawdown). El modelo solo puede argumentar con hechos que existen en known_facts.

Dónde: services/indicators.py

Mitigación de alucinaciones

hallucination guard

Toda cifra del texto generado debe existir en los hechos; si no, la frase se descarta y se reconstruye con la evidencia validada. Los porcentajes no se eximen.

Dónde: validate_agent_output()

Guardarraíles

guardrails

Reglas de negocio que corrigen la salida del modelo después de validarla: T1–T3, R1, S1, G1–G4. Cada corrección se publica como evento con before y after.

Dónde: guardrail_applied

Degradación elegante

graceful degradation / fallback

Si el proveedor falla, se agotan los pasos o la salida es inválida, el agente cae al camino determinista (rules_fallback) y lo deja anotado. El sistema nunca se bloquea por el LLM.

Dónde: LLMError → modo reglas

Debate y crítica entre agentes

multi-agent debate / self-critique

El escéptico busca contraargumentos y reta al técnico, que puede mantener (maintains) o ceder (concedes). El desacuerdo es información: baja la confianza final (guardarraíl G3).

Dónde: find_counterarguments(), disagreement

Ventana de contexto local

per-agent context, no shared memory

Cada agente tiene su propia lista de ChatMessage; nunca se comparte. Lo único que un agente exporta es su mensaje de salida. Esto acota el contexto y evita contaminación cruzada.

Dónde: messages local en run_agent_loop

Paso por referencia

artifact reference / blackboard

Las series de precios no viajan en los mensajes: se dejan en ctx.data[data_ref] y el mensaje lleva la referencia y un resumen. Es el patrón estándar para no inflar el contexto.

Dónde: data_ref, AgentContext.data

Abstracción de proveedor

provider abstraction / model-agnostic

Una interfaz (complete_json, chat) y tres implementaciones: mock, OpenRouter y Anthropic. Cambiar de modelo es configuración, no refactor.

Dónde: providers/

Determinismo para pruebas

mock provider / deterministic testing

MockLLMProvider llama las herramientas en el orden esperado y decide con las mismas reglas: la forma de la traza es idéntica con o sin red. Se puede enseñar y testear sin claves.

Dónde: mock_llm_provider.py

Control de concurrencia

throttling / backpressure

Un semáforo limita símbolos en paralelo y otro (ThrottledLLMProvider) limita llamadas simultáneas al modelo. Sin esto, un lote de símbolos dispara errores 429.

Dónde: max_parallel_symbols, LLM_MAX_CONCURRENCY

Observabilidad y trazabilidad

event sourcing / LLM tracing

Cada llamada, herramienta, aviso y decisión emite un evento numerado (seq). La UI no recibe estado: lo deriva de los eventos. Auditar el sistema es leer la traza.

Dónde: EventBus, frontend/lib/trace.ts

Contabilidad de tokens y coste

LLM FinOps

Cada llm_call_completed lleva tokens y USD; summarize_costs() agrega por agente. Permite responder "¿quién gasta más?" —normalmente el agente de riesgo, con 3–4 turnos.

Dónde: services/costs.py

Reproducibilidad / replay

deterministic replay

Al conectar el WebSocket se reenvía el historial completo y el cliente deduplica por seq. Reabrir una ejecución pasada es indistinguible de haberla visto en directo.

Dónde: lib/websocket.ts → mergeEvents

02Los dos modos: quién decide y quién redacta

Es la distinción más importante del proyecto y la que mejor explica la filosofía: el LLM se usa donde aporta (lenguaje, criterio, exploración) y no donde no aporta (aritmética, umbrales, política).

Quién decideLa regla determinista (rule_stance, rule_risk_level, decide).El modelo propone; las reglas quedan como referencia y guardarraíl.
Papel del LLMRedactor: convierte hechos en una explicación legible.Razonador: elige herramientas, pide datos, argumenta y concluye.
Llamadas al modeloUna por agente (complete_json).Varias por agente (chat en bucle, hasta AGENT_MAX_STEPS).
HerramientasNo se usan: los hechos ya vienen calculados.compute_indicators, compute_risk_metrics, request_history, challenge_technical.

La idea que hay que llevarse: las reglas nunca desaparecen. O deciden, o vigilan. Y como cada opinión guarda rule_reference, siempre se puede comparar en la misma pantalla lo que dijo el modelo con lo que habrían dicho las reglas —sin repetir la ejecución.

Así razona un agente en modo llm. El ejemplo es el agente de riesgo, que es el único que además habla con otro agente desde dentro de una herramienta.

No hay prompts sueltos ni plantillas externas: cada llamada al modelo se compone en código, por capas. Saber cuáles son —y cuál hay que tocar cuando algo sale mal— es media hora de lectura que ahorra días.

Dos cosas que no son texto libre y condicionan igual

Definiciones de herramientas

tool specs

Nombre, descripción y JSON Schema de argumentos, enviados como tools (OpenAI/OpenRouter) o tools con input_schema (Claude). Si el modelo no llama a una herramienta cuando debería, lo primero a revisar es su descripción, no el prompt de sistema.

Dónde: ToolSpec en llm_provider.py

Esquemas de salida

output schemas

TECH_SCHEMA, RISK_SCHEMA, SKEPTIC_SCHEMA, DECISION_SCHEMA, EXPLANATION_SCHEMA. Van como formato forzado si el proveedor lo soporta y, siempre, incrustados en el mensaje de usuario: cinturón y tirantes.

Dónde: cada agents/*.py

Ejemplo real: lo que recibe el agente de riesgo en modo llm

Tarea: risk_analysis

Instrucciones:
Eres el analista de riesgo. Debes asignar un nivel de riesgo (BAJO, MEDIO o ALTO) a la
serie descrita en <facts>. Invoca `compute_risk_metrics` para obtener volatilidad
anualizada, drawdown máximo y ATR relativo (no los estimes). Si `bars_used` es inferior
a `min_bars_recommended`, ... pide historial ampliado con `request_history` ... Cita
cada métrica usada en `evidence` con su nombre exacto.

<facts>
{ "symbol": "NVDA", "data_ref": "NVDA:130", "bars": 92, "first_date": "2026-04-15",
  "last_date": "2026-08-21", "last_close": 215.83, "min_bars_recommended": 200,
  "extended_history_days": 365 }
</facts>

Cuando hayas terminado de usar herramientas, responde ÚNICAMENTE con un objeto JSON que
cumpla este esquema:
{"type": "object", "properties": {
   "risk_level": {"enum": ["BAJO","MEDIO","ALTO"]},
   "confidence": ..., "evidence": ..., "summary": ..., "caveats": ...}, ...}

Fijate en lo que no hay: ni ejemplos de salida (few-shot), ni cadena de razonamiento forzada, ni una lista de veinte reglas defensivas. Tarea, instrucciones, hechos y formato.

Por qué los prompts son cortos y poco prescriptivos: la disciplina del sistema no descansa en que el modelo obedezca una lista larga de reglas, sino en la arquitectura. Los números solo llegan por herramientas, la validación descarta lo que no está en los hechos y los guardarraíles corrigen las salidas dudosas. El prompt explica la tarea; el código garantiza el resto. Efecto secundario valioso: cambiar de modelo (mock, OpenRouter, Claude) no obliga a reescribir prompts.

Qué queda de todo esto en la traza

Se registraDetalle
Sí — en llm_call_startedLa tarea, el proveedor, las herramientas ofrecidas y las claves de los hechos enviados.
Sí — en tool_calledArgumentos y resultado de cada herramienta: la prueba de qué miró realmente el modelo.
No — el texto del promptSe omite por volumen. Se puede reconstruir qué vio el modelo, pero no palabra por palabra.
Consecuencia práctica: si cambiás un prompt y el comportamiento se mueve, la traza te dice qué herramientas se ofrecieron y qué hechos había, pero no el texto exacto que se envió. Por eso versionar los prompts y registrar esa versión en llm_call_started aparece en las oportunidades de mejora.

05La cadena anti-alucinación

Cuatro filtros en serie. Ninguno confía en el anterior, y el último siempre es determinista.

1 · HECHOS      indicators.py calcula los números → known_facts
                (el modelo nunca ve datos crudos sin procesar)
        │
        ▼
2 · ESQUEMA     la respuesta debe encajar en el JSON Schema del agente
                enum inválido  →  hard error  →  se descarta TODA la salida
        │
        ▼
3 · VALIDACIÓN  validate_agent_output(clean, warnings, hard_errors)
                · evidencia que no existe en known_facts   → se elimina
                · confianza fuera de [0,1]                 → se acota
                · número en el texto sin hecho detrás      → texto reconstruido
        │
        ▼
4 · GUARDARRAÍL regla de negocio con la última palabra
                T1 · postura opuesta a las reglas con <2 evidencias → NEUTRAL
                R1 · riesgo 2 niveles por debajo de las reglas      → nivel de reglas
                G1 · COMPRA con riesgo ALTO                         → ESPERAR
                G3 · escéptico discrepa y técnico mantiene          → confianza ≤ 0.5
        │
        ▼
   SALIDA + rule_reference  ("qué habrían dicho las reglas")
Por qué importa: este es exactamente el patrón que se pide en producción cuando un LLM toca decisiones con consecuencias. El modelo aporta lenguaje y criterio; el código aporta los números y el límite. Y todo desacuerdo entre ambos queda registrado en lugar de esconderse.

06Preguntas y respuestas sobre la aplicación

Las 38 preguntas que aparecen al leer el código por primera vez —y las que conviene saber responder en una revisión técnica. Filtrá por tema.

1. ¿Por qué todos los mensajes tienen que pasar por deliver()?Arquitectura

Porque es el único punto donde un mensaje se hace observable. deliver() emite el mensaje al bus antes de entregarlo, aplica la latencia simulada y emite también la respuesta. Si un agente llamara a otro.process() directamente, el intercambio funcionaría pero no existiría para la UI, la auditoría ni el cálculo de costes: sería un canal lateral invisible.

Es una decisión de observabilidad, no de estilo: la garantía "todo lo que ocurrió está en la traza" solo se sostiene si el canal es único.

2. ¿Por qué el orquestador aparece en el enum AgentName si no es un BaseAgent?Arquitectura

Porque también envía y recibe mensajes: es emisor de los task_request y receptor de las opinion y la decision. Para que la UI pueda dibujar la arista, el remitente necesita un nombre válido. Lo que no tiene es process(): no se le puede pedir una tarea, él las reparte.

3. ¿Cuál es la diferencia real entre un mensaje y un evento?Arquitectura

Un mensaje es acción: cambia el estado de la conversación, alguien lo tiene que responder. Un evento es observación: cuenta que algo pasó y nadie lo responde.

La relación es de contención: cada mensaje genera un evento message_sent que lo lleva entero dentro (event.message). Pero hay eventos sin mensaje (llm_call_started, tool_called, guardrail_applied). Por eso la traza de eventos es un superconjunto de la conversación.

4. ¿Por qué POST /api/runs devuelve 202 y no el resultado?Arquitectura

Porque crear una ejecución y observarla son cosas distintas. Un análisis con LLM puede tardar decenas de segundos; bloquear la petición HTTP daría timeouts y haría imposible el streaming. Con 202 + run_id, el cliente abre el WebSocket y ve la conversación desarrollarse, puede desconectarse y volver, y puede seguir varias ejecuciones a la vez.

5. ¿Cómo se logra el paralelismo y por qué hay un semáforo?Arquitectura

Cada símbolo es una corrutina independiente lanzada con asyncio.gather. El semáforo (max_parallel_symbols, 3 por defecto) limita cuántas avanzan a la vez.

Sirve para dos cosas: proteger al proveedor de datos y al LLM de una ráfaga de peticiones, y mantener la demo legible —veinte símbolos simultáneos convierten el grafo en ruido.

6. ¿Por qué los agentes no pueden guardar estado en self?Arquitectura

Porque hay una sola instancia de cada agente compartida entre todos los símbolos. Si RiskAgent guardara el símbolo actual en self.symbol, dos conversaciones concurrentes se pisarían de forma no determinista y casi imposible de reproducir.

El estado por tarea vive en variables locales y cierres —mirá RiskAgent._analyze_llm → state, que es justamente el patrón a imitar.

7. ¿Qué es data_ref y por qué no se mandan los datos directamente?Arquitectura

Es un puntero a una serie de precios guardada en ctx.data. Si las 130 o 252 velas viajaran en el payload, cada evento message_sent pesaría cientos de kilobytes: la traza dejaría de ser legible, el WebSocket se saturaría y los JSON de backend/runs/ serían inmanejables.

El mensaje lleva la referencia más un resumen (bars, last_close), que es lo que un humano necesita para entender el intercambio.

8. ¿Cómo se reconstruye un hilo de conversación?Arquitectura

Con in_reply_to. Cada respuesta lleva el id de la petición que la originó, y la regla es estricta: una petición, exactamente una respuesta. El inspector de la UI usa ese campo para mostrar el enlace "responde a" y permitir navegar el hilo hacia atrás.

9. ¿Qué pasa si un símbolo falla a mitad del análisis?Arquitectura

Hay dos redes. La primera es error_reply(): un agente que no puede hacer su trabajo responde con un mensaje de tipo error (con code y reason), que el flujo trata como un resultado válido —típicamente termina en NO_ANALIZABLE.

La segunda es guarded(), un try/except de último recurso alrededor de analyze_symbol(). Un símbolo nunca se queda sin resultado y un fallo no arrastra a los demás.

10. Quiero cambiar el orden de la conversación. ¿Dónde toco?Arquitectura

Solo en Orchestrator.analyze_symbol(). Es el único sitio donde está escrito quién habla con quién y en qué orden. Los agentes no saben quién viene después de ellos, así que reordenar el guion no obliga a tocarlos.

La excepción son las comunicaciones directas (risk → market_data, skeptic → technical): esas viven dentro del agente que las inicia.

11. En modo rules, ¿para qué se usa el LLM?LLM

Solo como redactor. La postura ya la fijó la regla antes de llamar al modelo, y el prompt se lo dice explícitamente: "no cambies la postura; solo explícala". El modelo recibe un diccionario de hechos y devuelve {summary, facts_used, caveats}.

Si la explicación cita un número que no está en los hechos, se descarta y se usa una plantilla determinista (generated_by: rules). El resultado nunca depende del modelo.

12. ¿Cómo decide el modelo llamar a una herramienta?LLM

El agente le pasa la lista de herramientas disponibles como ToolSpec: nombre, descripción en lenguaje natural y JSON Schema de argumentos. El modelo responde con tool_calls en lugar de texto; el agente ejecuta el handler correspondiente y devuelve el resultado como mensaje de rol tool. El ciclo se repite hasta que el modelo responde con el JSON final o se alcanza AGENT_MAX_STEPS.

La calidad de la descripción de la herramienta es literalmente parte del prompt: es lo único que el modelo tiene para decidir cuándo usarla.

13. ¿Cómo puede una herramienta convertirse en un mensaje entre agentes?LLM

Porque el handler es una corrutina Python normal y puede hacer lo que quiera —incluido await self.send(market_data, info_request). Eso es request_history; y challenge_technical hace lo mismo hacia el técnico.

El efecto es elegante: el modelo "decide hablar con alguien", y esa decisión se materializa como un AgentMessage corriente que pasa por deliver() y se ve en el grafo igual que cualquier otro. No hay un canal especial para el LLM.

14. ¿Los agentes comparten la conversación con el modelo?LLM

No. Cada agente tiene su propia lista messages en memoria, local a la llamada. Lo único que un agente exporta es su AgentMessage de salida.

Esto es deliberado: mantiene el contexto pequeño (más barato y más preciso), evita que el razonamiento de uno contamine al otro, y hace que el escéptico juzgue la conclusión del técnico, no su monólogo interno.

15. ¿Qué pasa si el modelo entra en bucle o el proveedor falla?LLM

Si se superan AGENT_MAX_STEPS turnos sin JSON final, o el proveedor devuelve un error, se lanza LLMError y el agente cae al camino determinista, marcando la salida como mode: rules_fallback.

La ejecución nunca se bloquea por el LLM, y el fallback queda anotado: es una métrica útil —una tasa alta de rules_fallback indica un prompt o un esquema mal diseñado.

16. ¿Cómo se garantiza que la salida sea JSON válido?LLM

Con una cascada de degradación por proveedor. OpenRouterProvider intenta response_format: json_schema, y si el modelo no lo soporta baja a json_object y finalmente a texto parseado. AnthropicProvider usa output_config.format.

Y por encima está la validación: un JSON sintácticamente correcto pero con un enumerado inválido (stance: "MUY ALCISTA") es un hard error y se descarta igual.

17. ¿Cómo se calcula el coste de una ejecución?LLM

Cada llm_call_completed lleva su usage con tokens y USD; summarize_costs() los agrega por agente al terminar. OpenRouter suele dar el coste exacto (usage.cost) o se estima por catálogo; Anthropic se estima con una tabla de precios; el mock cuenta 0 y aproxima tokens como caracteres/4.

Como el coste sale de los eventos y no de un contador aparte, siempre cuadra con lo que se ve en la traza.

18. ¿Por qué existe MockLLMProvider si hay proveedores reales?LLM

Por tres razones. Permite ejecutar la demo sin claves ni red. Hace los tests deterministas y gratis. Y, sobre todo, produce una traza con la misma forma que la real: llama a las herramientas en el orden esperado y decide con las mismas reglas.

Ese último punto es el que hace que el proyecto enseñe el protocolo y no un modelo concreto.

19. ¿Para qué sirve ThrottledLLMProvider?LLM

Envuelve al proveedor real con un semáforo (LLM_MAX_CONCURRENCY). Con 3 símbolos en paralelo y hasta 4 agentes usando el modelo, es fácil superar el límite de peticiones por minuto del proveedor. El semáforo pone las llamadas en cola en lugar de coleccionar errores 429.

20. ¿Cómo cambio de proveedor o de modelo?LLM

Por configuración (config.py). Todos implementan la misma interfaz — complete_json() y chat()— así que ni el orquestador ni los agentes cambian.

Eso sí: cambiar de modelo cambia el comportamiento en modo llm. La forma honesta de comparar es correr el mismo lote de símbolos con dos modelos y mirar la tasa de guardarraíles aplicados y de desacuerdo con rule_reference.

21. ¿Dónde están los prompts? No veo ficheros .txt ni plantillasPrompts

Están todos en código, en tres capas: los prompts de sistema (SYSTEM_PROMPT y AGENT_SYSTEM_PROMPT) en providers/llm_provider.py; las instrucciones de tarea (RULES_INSTRUCTIONS, LLM_INSTRUCTIONS, CHALLENGE_INSTRUCTIONS) en cada agents/*.py; y el mensaje de usuario, que lo genera render_agent_prompt() a partir de una plantilla fija.

La ventaja es que un prompt no se puede cambiar sin pasar por revisión de código. La desventaja es que no están versionados de forma independiente ni registrados en la traza —de ahí la mejora propuesta.

22. ¿Qué diferencia hay entre SYSTEM_PROMPT y AGENT_SYSTEM_PROMPT?Prompts

Son los dos modos. SYSTEM_PROMPT es el del redactor (modo rules): define el rol como componente de una demo educativa y prohíbe explícitamente cambiar la postura que fijó la regla; solo puede explicarla, sin inventar números y sin lenguaje imperativo.

AGENT_SYSTEM_PROMPT es el del razonador (modo llm): define el rol como agente de un sistema multiagente, establece que los únicos datos válidos son <facts> más los resultados de herramientas, obliga a consultar herramientas antes de fijar postura, exige que cada evidence cite el nombre exacto de un hecho y que el último mensaje sea solo el JSON.

23. ¿Por qué los prompts son tan cortos? ¿No debería ser más prescriptivo?Prompts

Porque la disciplina no vive en el prompt, vive en la arquitectura. Los números solo entran por herramientas, la validación borra lo que no está en los hechos y los guardarraíles corrigen las conclusiones inaceptables. Añadir veinte reglas defensivas al texto daría una falsa sensación de control: lo que garantiza el comportamiento es el código que hay alrededor.

Además tiene un beneficio concreto: prompts cortos y poco específicos de un proveedor hacen que cambiar de modelo (mock, OpenRouter, Claude) no obligue a reescribirlos.

24. Si el modelo no llama a una herramienta cuando debería, ¿qué toco primero?Prompts

La descripción de la herramienta, no el prompt de sistema. El ToolSpec —nombre, descripción y JSON Schema de argumentos— es literalmente lo único que el modelo tiene para decidir cuándo usarla; en la práctica funciona como parte del prompt.

Segundo lugar donde mirar: las instrucciones de tarea del agente, que son las que dicen "invoca X primero". El prompt de sistema es lo último que hay que tocar, porque afecta a todos los agentes a la vez.

25. ¿Qué es exactamente el bloque <facts>?Prompts

Es la sección del mensaje de usuario que lleva el JSON de hechos ya calculados: símbolo, data_ref, número de velas, fechas, último cierre, y parámetros como min_bars_recommended o extended_history_days.

Su papel es doble: le da al modelo su único material factual autorizado, y define el universo contra el que después se validará la salida. Todo número que el modelo escriba y no esté en <facts> ni en un resultado de herramienta se descarta.

26. ¿Puedo ver el prompt exacto que se envió en una ejecución guardada?Prompts

No literalmente. El texto íntegro no se guarda en la traza porque sería demasiado voluminoso. Lo que sí queda es suficiente para reconstruir qué vio el modelo: llm_call_started registra la tarea, el proveedor, las herramientas ofrecidas y las claves de los hechos enviados, y tool_called lleva argumentos y resultados.

Es un punto débil conocido: si cambiás un prompt entre dos ejecuciones, la traza no te dice cuál se usó en cada una. Registrar una versión o un hash del prompt en llm_call_started lo resolvería con muy poco código.

27. ¿Cómo se impide que el modelo invente un número?Validación

Los números no los produce el modelo: los calcula services/indicators.py y se acumulan en known_facts (hechos iniciales + resultados de herramientas). Después, validate_agent_output() comprueba que toda cifra del texto exista ahí; si no, la frase se reemplaza por una construida con la evidencia validada.

Los porcentajes no se eximen: "subirá un 80 %" sin un hecho 0.8 detrás se descarta.

28. ¿Diferencia entre hard error y warning?Validación

Un hard error invalida la salida entera y fuerza el fallback a reglas; el caso típico es un enumerado fuera de vocabulario. Un warning es reparable: se elimina la evidencia inexistente, se acota la confianza a [0,1], se reconstruye el texto. La ejecución sigue, y queda un evento validation_warning.

El criterio es simple: si el sistema no puede saber qué quiso decir el modelo, descarta; si puede repararlo sin inventar, repara y lo anota.

29. ¿En qué se diferencia un guardarraíl de la validación?Validación

La validación es sintáctica y universal: pregunta "¿esta salida es bien formada y está anclada a hechos?". El guardarraíl es semántico y de negocio: pregunta "¿esta conclusión es aceptable?".

G1 —"COMPRA con riesgo ALTO → ESPERAR"— no corrige un error de formato: corrige una recomendación que el equipo ha decidido que no quiere emitir, aunque el modelo la argumente bien.

30. ¿Qué es rule_reference y para qué sirve?Validación

Es lo que las reglas deterministas habrían decidido para esa misma entrada, guardado junto a la opinión del modelo. La UI lo muestra como = reglas (coinciden) o reglas: X (difieren).

Da dos cosas gratis: comparación modelo-vs-reglas sin repetir la ejecución, y una métrica de calidad —si el modelo casi siempre coincide, no está aportando; si casi nunca coincide, hay que mirar el prompt o las reglas.

31. Si el guardarraíl siempre corrige al modelo, ¿no sobra el modelo?Validación

Una tasa alta y sostenida de guardrail_applied es exactamente esa señal, y por eso el evento existe y es medible. Pero conviene mirarlo por regla: T1 disparándose mucho sugiere un prompt que no exige evidencia suficiente; G1 disparándose mucho puede ser correcto (el mercado está volátil).

El valor del modelo en este sistema está sobre todo en la explicación, la exploración de datos y el debate —no en ganarle a un umbral.

32. ¿Por qué el frontend no tiene estado propio?Frontend

Porque cualquier estado paralelo se desincroniza. La UI recibe una lista de eventos y deriva todo de ella en lib/trace.ts: los símbolos de run_started, el estado de cada nodo de agent_started/completed/error, los resultados de symbol_completed, los costes de llm_call_completed.usage.

La consecuencia práctica: si algo no se puede mostrar, no falta código en el frontend, falta un evento en el backend.

33. ¿Cómo funciona el replay de una ejecución pasada?Frontend

Al conectar a WS /ws/runs/{id}, el servidor reenvía el historial completo y después sigue con los eventos nuevos. El cliente trata la ráfaga inicial como replay (sin animaciones) y luego anima en vivo.

Como el estado se deriva de los eventos, reabrir una ejecución con ?run=<id> es indistinguible de haberla visto en directo. Es event sourcing puro.

34. ¿Por qué hay que deduplicar por seq?Frontend

Porque el historial y el streaming pueden solaparse: un evento emitido mientras se envía el backlog puede llegar dos veces. Como seq es monótono y único por ejecución, mergeEvents lo usa como clave para deduplicar y ordenar. También permite reconectar sin duplicar la traza.

35. Quiero mostrar algo nuevo en la UI. ¿Qué toco?Frontend

Primero preguntá si el dato ya está en algún evento. Si está, es un cambio de lib/trace.ts más el componente. Si no está, el cambio empieza en el backend: añadir el campo al evento existente o crear un tipo de evento nuevo.

Lo que nunca hay que hacer es traer el dato por otra vía (un endpoint REST paralelo, un cálculo en el cliente): eso rompe el replay, porque la ejecución guardada dejaría de contener todo lo necesario para reconstruir la pantalla.

36. ¿Cómo pruebo el sistema sin claves de API?Operación

Con el proveedor mock de LLM y el de datos de mercado. La traza tiene la misma forma que la real —mismos eventos, mismas herramientas, mismos guardarraíles— y el coste es cero. Es el modo recomendado para el primer día y para los tests de regresión.

37. ¿Dónde quedan guardadas las ejecuciones?Operación

En memoria mientras corre (RunStore) y en disco al completarse: backend/runs/<run_id>.json con la ejecución y todos sus eventos. Eso es lo que permite el replay.

Es la limitación operativa más clara del diseño actual: no sobrevive a un despliegue con varias instancias, ni tiene política de retención. Está en la lista de mejoras.

38. ¿Cómo añado un agente nuevo?Operación

Cuatro pasos: (1) añadir el nombre al enum AgentName; (2) crear la clase heredando de BaseAgent e implementar process(), con su esquema JSON y su regla determinista de referencia; (3) registrarlo en el Orchestrator compartiendo el mismo AgentContext; (4) darle un turno en el guion de analyze_symbol() y decidir quién consume su opinión.

En el frontend, idealmente, no hay que tocar nada: el grafo y la traza se construyen a partir de los eventos.

07Oportunidades de mejora

Ordenadas por área. Cada punto indica el impacto (qué se gana) y el esfuerzo estimado. Nada de esto es un defecto del proyecto: es la lista natural de "qué haría falta para llevarlo a producción o para que enseñe todavía más".

Arquitectura y escalabilidad

Lo que hoy funciona perfecto en una máquina y se rompe con dos.

Persistencia real en lugar de memoria + JSON

RunStore vive en el proceso y vuelca a backend/runs/*.json. Con más de una instancia detrás de un balanceador, un espectador puede conectarse al nodo que no tiene su ejecución. Mover a Redis (estado vivo + pub/sub para el WebSocket) y Postgres o S3 (histórico) resuelve replay y escalado horizontal a la vez.

Impacto altoEsfuerzo medioBloqueante para producción
Ciclo de vida de ctx.data

Las series se acumulan en un diccionario en memoria y no se ve una política de liberación. En una sesión larga con muchos símbolos es una fuga silenciosa. Un TTL o un LRU por ejecución, liberado en run_completed, lo cierra.

Impacto altoEsfuerzo bajo
Timeouts y cancelación por mensaje

deliver() espera indefinidamente a que el destinatario responda. Un agente colgado en una llamada de red bloquea su conversación entera. Un asyncio.wait_for por mensaje, que produzca un error canónico al vencer, más cancelación de la ejecución desde la API (DELETE /api/runs/{id}), lo hace robusto.

Impacto altoEsfuerzo bajo
El guion como dato, no como código

El flujo está escrito a mano en analyze_symbol(). Extraerlo a una definición declarativa (un grafo de nodos con dependencias) permitiría flujos alternativos, ejecutarlos desde la configuración y —muy valioso para la demo— dibujar el guion antes de correrlo.

Impacto medioEsfuerzo medioAlto valor didáctico
Reintentos y cortocircuito por proveedor

Hoy un fallo del LLM cae directo a reglas. Un reintento con espera exponencial ante 429 o 5xx recuperaría muchos casos, y un circuit breaker evitaría castigar a todos los símbolos cuando el proveedor está caído.

Impacto medioEsfuerzo bajo
WebSocket con since_seq

Al conectar se reenvía el historial completo. En ejecuciones largas eso es una ráfaga innecesaria al reconectar. Aceptar un cursor (?since_seq=N) y comprimir el canal reduce el coste sin cambiar la semántica.

Impacto bajoEsfuerzo bajo

Calidad del razonamiento multiagente

Dónde el sistema podría razonar mejor, no solo más.

El escéptico debería poder retar a todos

Hoy solo reta al técnico. Permitirle cuestionar también el nivel de riesgo y la decisión final —con el mismo protocolo challenge / respuesta— haría el debate simétrico y expondría un patrón multiagente más general.

Impacto altoEsfuerzo medio
Debate de varias rondas con criterio de convergencia

El reto es de un solo turno. Permitir N rondas hasta que no aparezcan objeciones nuevas (o se agote un presupuesto) es el patrón de multi-agent debate completo, y es visualmente espectacular en el grafo.

Impacto medioEsfuerzo medio
Autoconsistencia en decisiones de bajo consenso

Cuando el escéptico discrepa, muestrear k salidas del agente de decisión y quedarse con la mayoría (self-consistency) reduce mucho la varianza, a cambio de coste. Aplicarlo solo en los casos dudosos lo hace asequible.

Impacto medioEsfuerzo bajo
Un agente de contexto cualitativo (RAG)

Todo el sistema es cuantitativo. Un agente de noticias o sentimiento con recuperación de documentos añadiría el concepto que hoy falta —retrieval-augmented generation— y obligaría a extender el anclaje a hechos: citar la fuente, no solo el número.

Impacto medioEsfuerzo alto
Bucle de realimentación: ¿acertó?

El sistema decide y olvida. Guardar la decisión y contrastarla con el precio a 5, 20 y 60 sesiones daría una métrica real de calidad y permitiría comparar honestamente rules contra llm. Es la diferencia entre una demo y un experimento.

Impacto altoEsfuerzo medio

Fiabilidad del LLM y evaluación

Cómo saber que un cambio de prompt o de modelo mejoró algo.

Suite de evaluación con trazas de referencia

Es la carencia más importante. Un conjunto fijo de símbolos con salidas esperadas, ejecutado en CI contra el mock y periódicamente contra el modelo real, midiendo tasa de rules_fallback, de guardrail_applied, de validation_warning y de desacuerdo con rule_reference. Sin esto, tocar un prompt es a ciegas.

Impacto altoEsfuerzo medioPrioridad 1
Versionar los prompts y registrarlo en la traza

Los prompts viven en código —bien— pero no tienen versión propia ni quedan registrados: la traza guarda la tarea, el proveedor, las herramientas ofrecidas y las claves de hechos, no el texto. Basta con un identificador de versión (o un hash del texto compuesto) por cada capa —SYSTEM_PROMPT, AGENT_SYSTEM_PROMPT, las *_INSTRUCTIONS del agente— emitido en llm_call_started. Con eso, comparar dos ejecuciones deja de ser arqueología.

Impacto altoEsfuerzo bajoHabilita todo lo demás
Tratar las descripciones de herramientas como superficie de prompt

La descripción de un ToolSpec determina si el modelo la llama o no, pero hoy se edita como si fuera un comentario. Debería entrar en el mismo circuito que los prompts: versión, revisión y un caso en la suite de evaluación que compruebe que la herramienta se invoca cuando corresponde (por ejemplo, que request_history se llame si bars_used < min_bars_recommended).

Impacto medioEsfuerzo bajo
Medir la sensibilidad del prompt entre modelos

La tesis del proyecto es que los prompts son cortos porque la arquitectura sostiene la disciplina. Es una afirmación comprobable: correr el mismo lote con dos o tres modelos y comparar tasa de guardarraíles, de validation_warning y de rules_fallback. Si los números se mantienen, la tesis queda demostrada; si se disparan con un modelo, se sabe exactamente dónde reforzar.

Impacto medioEsfuerzo medio
Validación semántica, no solo sintáctica

Hoy se comprueba que los números existan, pero no que la evidencia sostenga la conclusión: una postura ALCISTA citando un RSI de 78 pasa el filtro. Una regla de coherencia evidencia↔postura por agente cerraría el hueco.

Impacto medioEsfuerzo medio
Caché de respuestas y de prompt

El mismo símbolo el mismo día con el mismo modelo produce la misma entrada. Cachear por (símbolo, fecha, modelo, versión de prompt) abarata las demos repetidas; el prompt caching del proveedor reduce además el coste de la parte fija del contexto.

Impacto medioEsfuerzo bajo
Streaming de tokens

Hoy cada turno del modelo es opaco hasta que termina. Emitir deltas dejaría ver el razonamiento formándose, lo que en una demo pedagógica vale mucho y reduce la latencia percibida.

Impacto bajoEsfuerzo medio

Seguridad y coste

Lo que hay que resolver antes de exponerlo fuera de casa.

Presupuesto por ejecución

No hay tope de gasto: un lote grande en modo llm puede costar bastante más de lo previsto. Un máximo en USD por ejecución que, al alcanzarse, degrade a reglas y lo anote, convierte el coste en una decisión explícita.

Impacto altoEsfuerzo bajo
Superficie de inyección de prompt

Los símbolos vienen del usuario y acaban en el prompt. Hoy el riesgo es bajo porque normalize_symbols() los limpia y la salida está encorsetada por esquema y validación —pero en cuanto entre texto libre (noticias, comentarios), hará falta separar datos de instrucciones explícitamente y tratar todo lo externo como no confiable.

Impacto medioEsfuerzo bajoCrítico si se añade RAG
Autenticación y límite de peticiones

POST /api/runs gasta dinero real y no parece tener autenticación ni rate limiting. Ambos son imprescindibles antes de exponer la app en internet.

Impacto altoEsfuerzo bajo
Retención y contenido de los ficheros de ejecución

Los JSON de backend/runs/ guardan texto generado por el modelo y crecen sin límite. Conviene política de retención, y revisar que no se persistan cabeceras, claves ni datos sensibles en los eventos de llamada.

Impacto medioEsfuerzo bajo
Trazas en un estándar abierto

El EventBus ya es un trazador; exportarlo a OpenTelemetry (un span por agente, por llamada al modelo y por herramienta) permitiría usar herramientas de observabilidad de LLM existentes sin construir nada propio.

Impacto bajoEsfuerzo medio

Producto, pruebas y experiencia

Detalles que multiplican el valor didáctico con poco código.

Comparar dos ejecuciones lado a lado

La misma cartera en modo rules y en modo llm, en dos columnas, con las diferencias resaltadas. Es la mejor forma de enseñar qué aporta y qué arriesga el modelo, y todo el dato necesario ya está guardado.

Impacto altoEsfuerzo medio
Modo paso a paso

Hoy el ritmo se controla con message_delay_ms. Un control de pausa / siguiente mensaje convertiría la demo en algo narrable a velocidad de quien explica, sin adivinar el retardo correcto de antemano.

Impacto medioEsfuerzo bajo
Exportar la traza

Un botón para bajar la conversación como Markdown o PDF —incluyendo evidencias, objeciones y guardarraíles— hace que la ejecución sirva como material de estudio o como anexo de una revisión técnica.

Impacto medioEsfuerzo bajo
Tests de invariantes del protocolo

Tres pruebas baratas que protegen el diseño: toda respuesta lleva in_reply_to válido; ningún mensaje llega a un agente sin haber pasado por deliver(); los seq son estrictamente monótonos y sin huecos. Más pruebas de propiedades sobre los indicadores.

Impacto altoEsfuerzo bajo
Aviso explícito de que no es asesoramiento financiero

La app emite palabras como COMPRA y VENTA. Un descargo visible en la interfaz y en la traza exportada evita malentendidos y es lo correcto aunque el dominio sea una excusa.

Impacto medioEsfuerzo bajo
Si hubiera que elegir tres: la suite de evaluación con trazas de referencia (sin ella no se puede mejorar nada con criterio), la persistencia real (sin ella no se puede desplegar) y el bucle de realimentación con el precio posterior (sin él no se puede decir si el sistema acierta).
